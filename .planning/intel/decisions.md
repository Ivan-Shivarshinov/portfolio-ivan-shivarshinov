# Решения (decisions.md)

Источник: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md (ADR, confidence: high).
Статус всех решений: proposed — ADR не зафиксирован как locked.

## Решение 1: Гибридная модель разработки — Astro + AI-агент + Stacki + Git
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Связка «Astro + AI-агент + Stacki» — основа гибридной производственной среды портфолио. Astro — среда и исходный код проекта. AI-агент — программная и архитектурная рабочая поверхность. Stacki — визуальная рабочая поверхность над тем же Astro-кодом: открывает существующий Astro-проект, читает страницы, layouts, компоненты и props, запускает astro dev, показывает live preview и сохраняет изменения обратно в исходные файлы; предусмотрены Git-операции и переход к редактору кода. Git — история, страховка и механизм согласования изменений. Stacki не создаёт второй проект и не экспортирует сайт из собственного формата; сайт в любом случае строится на Astro. Webflow остаётся частью опыта, но не платформой портфолио.
- scope: Astro, Stacki, AI-агент, Git, Webflow (как опыт)

## Решение 2: Единый источник истины — файлы Astro-проекта в Git
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Ни один инструмент не должен становиться отдельным источником истины. Источником истины всегда остаются файлы Astro-проекта в Git. Распределение ролей: Astro — архитектура, компоненты, маршруты, контент, сборка и конечный код; AI-агент — создание и изменение кода, логика, рефакторинг, адаптив, SEO, тестирование; Stacki — визуальная проверка, композиция, контент, props, variants, стили и порядок элементов; редактор кода — точные реализации, отладка и ручные точечные изменения; Git — контроль версий, сравнение изменений, ветки, откат и безопасное объединение работы; preview deployment — проверка реального сайта на устройствах и перед публикацией.
- scope: архитектура, Git, workflow

## Решение 3: Архитектура проекта и компонентные правила
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Рекомендуемая структура: src/components/{ui, sections, case-study, islands}, src/content (Content Collections: projects, notes), src/data (JSON: services, skills, testimonials, tools), src/layouts, src/pages, src/styles (tokens.css, global.css, utilities.css, motion.css). Страница собирается из осмысленных секций (Hero, SelectedProjects, Expertise, About, Contact); не создавать компонент для каждого div (компонент создаётся при переиспользовании, самостоятельной визуальной роли, вариантах, логике или удобстве правки как цельного объекта). Props — семантические (layout: split|stacked|editorial; density: compact|default|spacious; theme: light|dark|accent), а не сырые значения (paddingTop, paddingBottom, headingWidth, imageLeft). Адаптивность живёт внутри компонентов (смена сетки, складывание колонок, ограничение ширины текста, масштабирование отступов, обработка изображений, упрощение анимации). Design tokens создаются до активной визуальной сборки: цвета (bg-primary, bg-secondary, text-primary, text-muted, accent), шрифты (display, body), отступы (space-1..3), радиусы, контейнеры (main, wide), motion-токены. Для первого прототипа предпочтителен обычный CSS со свойствами и переменными, а не utility-first архитектура (практическая рекомендация до проверки совместимости со Stacki).
- scope: компонентная архитектура, design tokens, совместимость со Stacki

## Решение 4: Разделение данных
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Content Collections — для проектов, полноценных кейсов, статей и заметок (валидация структуры, типизация, build-time коллекции; Markdown/MDX/JSON/YAML и удалённые источники). JSON — для небольших повторяемых наборов (компетенции, инструменты, короткие отзывы, услуги, логотипы, группы показателей, пункты процесса). Frontmatter страницы — для данных, относящихся только к одной странице. Props компонентов — для визуальных вариантов и поведения (theme, size, layout, density, alignment, mediaPosition, showLabel, showMetrics, animation, background). Контент не следует без необходимости смешивать с визуальными вариантами.
- scope: данные, Content Collections, JSON, frontmatter, props

## Решение 5: Workflow разработки
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Этап 0 — технический spike: небольшой экспериментальный Astro-проект с одной страницей, проверка в Stacki (открытие проекта, чтение компонентов и props, перестановка секций, variants, scoped styles, глобальные stylesheets, CSS variables, breakpoints, JSON-коллекции, frontmatter, вложенные элементы и loops, компоненты со slots, View Transitions, vanilla JavaScript, один React-компонент, внешнее изменение файлов агентом, git diff); результат — внутренний документ о покрытии конструкций Stacki. Этап 1 — формирование основы агентом: Astro-проект, TypeScript strict, базовая структура папок, глобальные design tokens, reset и typography, основные layouts, общий SEO-компонент, sitemap, базовые UI-компоненты, схемы Content Collections, проверки сборки. Этап 2 — визуальная система: типографика → цвет → контейнеры и сетка → отступы → кнопки и ссылки → медиа-компоненты → заголовки секций → карточки проектов → навигация → footer → motion tokens. Этап 3 — цикл разработки секции из 8 шагов: краткий контракт → базовый Git-коммит → реализация агентом → техническая проверка → визуальный проход в Stacki → анализ diff → cleanup агентом → финальный коммит. Правило одновременной работы: можно работать над одним проектом параллельно, но не следует одновременно записывать изменения в один и тот же файл; оптимальный цикл: агент завершает операцию → изменения появляются в Stacki → визуальный проход → агент анализирует итоговый diff → Git фиксирует состояние.
- scope: процесс разработки, Stacki, AI-агент, Git

## Решение 6: Порядок выбора технологий анимации и интерактивности
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Не превращать весь сайт в клиентское приложение ради нескольких эффектов. Порядок выбора технологии: CSS transitions и animations → vanilla JavaScript в Astro-компоненте → View Transitions для переходов между страницами → React, Svelte или другая island-компонента для действительно сложной интерактивности. Astro-компоненты по умолчанию создают статический HTML без клиентского runtime; JavaScript загружается только для явно обозначенных islands с управлением моментом загрузки (после простоя браузера или появления во viewport). Astro View Transitions поддерживают анимацию навигации, перенос элементов между страницами, собственные анимации, fallback и автоматическое соблюдение prefers-reduced-motion.
- scope: анимация, интерактивность, islands, View Transitions

## Решение 7: Quality gates перед merge
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Перед merge страницы или крупной функции выполняются проверки. Код: TypeScript check, production build, проверка ошибок в консоли, проверка лишних зависимостей, проверка размера клиентского JavaScript, просмотр Git diff. Адаптив: широкий desktop, обычный desktop, landscape tablet, portrait tablet, mobile, узкий mobile, реальные устройства когда возможно. Доступность: клавиатурная навигация, видимый focus, корректная иерархия заголовков, alt-тексты, достаточный контраст, prefers-reduced-motion, отсутствие критичной информации только в hover, корректные labels у форм. SEO: уникальные title и description, canonical, Open Graph, Twitter cards, sitemap (через @astrojs/sitemap), robots, структурированные данные где уместно, внутренние ссылки, корректные статусы страниц, отсутствие случайных тестовых маршрутов. Производительность: изображения соответствуют реальному размеру отображения, below-the-fold изображения ленивые, видео не загружается без необходимости, шрифты оптимизированы, нет лишних islands, тяжёлая интерактивность загружается только при необходимости.
- scope: качество, адаптив, доступность, SEO, производительность

## Решение 8: Baseline стека
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Astro — основной framework; TypeScript strict — проверка структуры props и данных; Astro components — основная UI-модель; scoped CSS + CSS variables — базовая стилизация; Content Collections — проекты и статьи; Markdown — обычный текстовый контент; MDX — только для кейсов с интерактивными компонентами; vanilla JavaScript — небольшие интеракции; React island — только для сложных интерактивных блоков; Astro Image/Picture — изображения; Astro View Transitions — навигационные переходы; Astro Sitemap — sitemap; Stacki — визуальная рабочая поверхность; GitHub — репозиторий и история; Vercel, Netlify или Cloudflare — preview и production deployment; AI-агент — реализация, рефакторинг, тесты и системные изменения. Не следует заранее добавлять: тяжёлый клиентский framework для всего сайта, внешнюю CMS, базу данных, глобальный state manager, сложный backend, большое количество анимационных библиотек, utility framework до проверки его совместимости со способом работы в Stacki.
- scope: стек

## Решение 9: Риски Stacki и компенсации
- source: docs/Техническая стратегия портфолио Astro + AI-агент + Stacki.md
- status: proposed
- decision: Ранняя стадия продукта (v0.1.3): ожидать баги и неполное покрытие Astro-конструкций; компенсация — Git перед каждым визуальным проходом, отдельные feature branches, production build после изменений, не обновлять Stacki посреди важной итерации без коммита, проект полностью работоспособен без Stacki. Неполное визуальное представление сложного кода: предусмотрен code fallback; компенсация — осмысленные секционные компоненты, варианты через props, повторяемый контент отдельно от сложной логики, визуальный редактор для подходящих операций, код и AI для остальных. Конфликты изменений: не изменять один файл одновременно, короткие итерации, просмотр diff, отдельные коммиты для структурных и визуальных изменений. Накопление случайных CSS-значений: design tokens, ограниченные variants, регулярный cleanup агентом, запрет на бесконтрольные one-off значения. Подстраивание всего проекта под Stacki: не жертвовать качеством Astro-кода — строить хороший Astro-проект, но выбирать среди одинаково хороших архитектур ту, что лучше представляется визуально. Прекращение развития Stacki не угрожает проекту: конечным артефактом остаётся обычный Astro-код, Stacki имеет открытый исходный код и MIT-лицензию.
- scope: риски, Stacki, Git
