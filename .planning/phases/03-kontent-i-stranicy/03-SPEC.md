# Phase 3: Контент и страницы — Specification

**Created:** 2026-08-03
**Ambiguity score:** 0.15 (gate: ≤ 0.20)
**Requirements:** 9 locked

## Goal

Все разделы сайта (Home, Work, Case Study, Lab, About, Contact) наполняются реальным контентом по позиционированию «Product-minded Web Developer»: формула обещания на первом экране, 5–6 кейсов со страницами-разборами по схеме «проблема → ответственность → решение → результат», иерархия компетенций Build/Improve/Extend, превью Lab и контактные каналы — в спокойном, конкретном тоне без хайпа.

## Background

Фаза 2 завершена (2026-08-03): визуальная система «Calm Interface, Active Work» готова, но **реального контента на сайте нет**:

- `src/pages/index.astro` — hero-оболочка D-13 (метка «01 / HOME», имя, CTA «Смотреть работы»); текста формулы обещания нет (по hero-concept D-12/D-13 формула добавляется в фазе 3 под именем, CTA остаётся последним действием)
- `src/pages/work.astro` — SYSTEM DEMO-блок с 2 фикстурными карточками («Проект „Терракота"», «Проект „Олива"», маркер `// fixture: replaced in phase 3`)
- `src/pages/lab.astro`, `about.astro`, `contact.astro` — empty-state-заглушки «раздел в разработке» (D-04)
- `src/content/projects/` — 0 записей (только `.gitkeep`); схема готова: frontmatter `slug/title/summary/role/stack/year/status/client-type/order/titleEn?`, четыре вопроса — в MDX-теле (D-05); `notes` пуста намеренно (D-07)
- `src/data/services.json` — 3 записи, не отражающие иерархию Build/Improve/Extend
- Компоненты для контента готовы: ProjectCard (темы 5-enum), Tag, Media, SectionHeading, иконки IconMail/IconCopy/IconGithub/IconTelegram
- Footer без ссылок (D-03: контент — фаза 3); навигация 5 маршрутов фиксирована
- Верификация: `check-seo.mjs` жёстко ожидает ровно 5 страниц и 5 url в sitemap — требует обновления под страницы кейсов
- Репозиторий GitHub public (`portfolio-ivan-shivarshinov`) — контент и скриншоты станут публичными

Триггер фазы: ROADMAP SC1–5 фазы 3 («первый экран с формулой обещания», «путь Home → Work → Case Study → Contact», «кейсы отвечают на 4 вопроса», «Capabilities иерархией Build/Improve/Extend, Lab Preview», «тон без пафоса»).

## Requirements

1. **Формула обещания на первом экране**: На / под именем рендерится формула обещания из REQ-main-promise и категория «веб-разработчик с продуктовым подходом» / «Product-minded web developer»; CTA «Смотреть работы» остаётся последним действием секции.
   - Current: hero-shell D-13 — только имя «Иван Шиваршинов» + CTA; текста формулы нет
   - Target: под именем — формула обещания (рекомендуемый текст REQ-main-promise, в т.ч. «Создаю и развиваю сложные сайты, контентные системы и веб-инструменты…») + категория; без ярлыков-клише; CTA — финальный элемент hero
   - Acceptance: собранная / содержит текст формулы обещания и категорию; на странице не встречаются ярлыки Product Engineer / AI Product Developer / AEO/GEO Specialist / Web Systems Specialist / AI-native Developer; CTA «Смотреть работы» — последний элемент секции

2. **Work: 5–6 реальных кейсов из коллекции**: Коллекция `projects` содержит от 5 до 6 реальных записей с контентом по схеме «проблема → ответственность → решение → результат»; Work рендерит карточки из коллекции; фикстурные карточки SYSTEM DEMO удалены.
   - Current: 0 записей; work.astro — SYSTEM DEMO с фикстурами
   - Target: 5–6 MDX-записей с реальным контентом (4 вопроса в теле, D-05); `/work` — список карточек из коллекции; каждая карточка имеет тему из 5-enum (terracotta/clay/olive/slate/plum)
   - Acceptance: проверка числа записей — от 5 до 6 включительно, падает при 4 и при 7; grep по dist/`/work`: маркер «SYSTEM DEMO» и фикстурные названия отсутствуют; каждая карточка рендерит title, meta (role · year), summary, тему

3. **Страницы кейсов /work/{slug}/**: Для каждого кейса генерируется отдельная страница-разбор с четырьмя разделами и явным разделением личного вклада, вклада команды и итогового эффекта; все новые страницы попадают в sitemap и имеют уникальные пары title/description.
   - Current: динамического маршрута нет; маршрут не существует
   - Target: `/work/{slug}/` для каждой записи; 4 раздела (проблема → ответственность → решение → результат); уникальные SEO-метаданные; check-seo обновлён под фактическое число страниц
   - Acceptance: для каждой из 5–6 записей в dist существует `work/{slug}/index.html`; на странице присутствуют 4 раздела; sitemap-index.xml → дочерний urlset содержит все маршруты кейсов; `check-seo.mjs` обновлён (ожидаемое число страниц = факт) и зелёный

4. **Home: секция «Избранные работы»**: На / появляется секция с 2–3 карточками из коллекции, ведущими на страницы кейсов.
   - Current: на / только hero-shell
   - Target: секция с SectionHeading + 2–3 ProjectCard из реальных записей → `/work/{slug}/`
   - Acceptance: на / присутствует секция с 2–3 ссылками на `/work/{slug}/`; карточки взяты из коллекции (не фикстуры)

5. **About: полный набор блоков**: Страница содержит историю/профиль, «с кем работаю» (аудитории из REQ-audience), компетенции иерархией Build/Improve/Extend и траекторию роста из трёх ступеней.
   - Current: empty-state «раздел в разработке»
   - Target: 4 блока: профиль/история; аудитории и ситуации клиента (запустить / привести в порядок / развивать / расширить); компетенции Build/Improve/Extend с иерархией «понятный результат → доказанная специализация → коммерческое усиление → направление роста»; траектория Product-minded Web Developer → Web Product Developer → Product Engineer
   - Acceptance: на /about присутствуют 4 блока (проверяется структурно); компетенции поданы тремя группами Build/Improve/Extend с примерами; траектория — 3 ступени; длинный список инструментов не является центром страницы

6. **Lab: превью направлений + процесс**: Страница показывает мост к продуктам, AI и автоматизациям (направления) и описание процесса экспериментов; реальные эксперименты не включаются.
   - Current: empty-state «раздел в разработке»
   - Target: блок направлений (AI-воркфлоу, автоматизации, внутренние инструменты — «что здесь появится») + блок процесса (как устроены эксперименты); честный статус отсутствия готовых экспериментов
   - Acceptance: на /lab присутствуют 2 блока (направления + процесс); контент не притворяется, что эксперименты существуют (нет ссылок на готовые эксперименты); коллекция notes остаётся пустой

7. **Contact + Footer: каналы из единого источника**: Contact рендерит каналы email (mailto + копирование), Telegram и GitHub; футер получает ссылки на те же контакты; данные заданы одним источником.
   - Current: empty-state; футер без ссылок (D-03)
   - Target: на /contact ровно 3 канала (email, Telegram, GitHub) без формы и без LinkedIn; футер — ссылки на те же контакты из того же источника
   - Acceptance: на /contact присутствуют ровно 3 канала (нет LinkedIn, нет формы); mailto-ссылка корректна; копирование email в буфер работает (или корректный fallback); ссылки на /contact и в футере идентичны (единый источник данных); в футере ≥1 ссылка контакта

8. **Скриншоты: ≥1 реальный на кейс, без дублей**: Каждый кейс имеет минимум один реальный скриншот (файл в репозитории), подключённый в карточку и/или страницу; дубли файлов между кейсами запрещены.
   - Current: изображений в репозитории нет; Media рендерит пустой фрейм
   - Target: у каждой записи projects ≥1 скриншот реального интерфейса (предоставлен пользователем), задействованный в карточке или странице кейса
   - Acceptance: у каждой записи есть ≥1 файл изображения в репозитории, используемый карточкой или страницей кейса; ни один файл изображения не используется в двух разных кейсах; кейс с пустым Media-фреймом — FAIL фазы

9. **Тон: denylist + ручная проверка**: Тексты всего сайта соответствуют REQ-tone (спокойный, конкретный, без хайпа); автоматический denylist хайповых слов/паттернов + финальная ручная проверка по спискам «использовать/избегать».
   - Current: контента нет — тон проверять не на чем
   - Target: check-скрипт с непустым denylist (из списков «избегать» REQ-tone: хайповый AI-first язык, «революционные решения», лишние англицизмы, образ гения-одиночки) + ручной проход при UAT
   - Acceptance: denylist непустой (≥10 записей) и имеет self-test с фикстурой-нарушителем (фикстура FAIL / чистый текст PASS); прогон denylist по собранным страницам — зелёный; ручная проверка по спискам «использовать/избегать» зафиксирована в верификации/UAT

## Boundaries

**In scope:**
- Контент Home: формула обещания + категория + секция «Избранные работы»
- Контент Work: 5–6 записей в коллекции projects + страницы-разборы `/work/{slug}/`
- Контент About: 4 блока (профиль, аудитории, компетенции B/I/E, траектория)
- Контент Lab: превью направлений + описание процесса
- Контент Contact: 3 канала (email/TG/GitHub) + ссылки в футере из единого источника
- Скриншоты кейсов как файлы в репозитории
- Обновление check-seo (число страниц) и новый denylist-скрипт тона
- Удаление фикстурных карточек SYSTEM DEMO

**Out of scope:**
- Реальные эксперименты Lab (LAB-01…04, v2) — отложены в v2, в фазе 3 Lab — превью и процесс
- EN-версия сайта — D-08: поля локали опциональны, EN-страницы не входят
- Контент notes (блог/заметки) — коллекция остаётся пустой (D-07)
- Формы, бэкенд, внешняя CMS, глобальный state — запрещено ADR (статик SSG)
- LinkedIn в контактах — решение пользователя (3 канала: email, Telegram, GitHub)
- Интерактивный индекс работ и переход «список → кейс» — фазы 4–5
- View Transitions и motion-слой — фаза 5
- SEO-полировка, производительность, a11y-аудит — фаза 6
- Изменение навигации (5 маршрутов и метки фиксированы) и палитры тем (5-enum)

## Constraints

- Статический SSG (Astro 7): ноль клиентского JS-фреймворка, ноль бэкенда; контактные каналы — прямые ссылки (mailto, https)
- Контент — на русском (D-06/D-08); латиница только в моно-слое (метки, «Product-minded web developer» в формуле)
- Схемы коллекций не расширяются произвольно: добавление поля (например, `theme`) — только при необходимости с обоснованием; механизм назначения темы кейсам — решение discuss/plan
- Палитра тем фиксирована: terracotta/clay/olive/slate/plum (D-07); контраст ≥ 4.5:1 (check-contrast)
- Контент кейсов пишет агент из материала пользователя; пользователь утверждает каждый кейс (схема «материал от вас → агент пишет → вы утверждаете»)
- Названия клиентов — реальные, где допустимо; при NDA — анонимизация обязательна (K2)
- Скриншоты — реальные артефакты работы (K4); репозиторий public — без чувствительных данных
- Контент ложится в существующие компоненты (ProjectCard, Media, Tag, SectionHeading, Button, Link) — без one-off стилей (check-tokens)
- Требование копирования email в буфер реализуется в рамках бюджета клиентского JS (варианты и fallback — discuss/plan)
